# AxiTime — Interpreter CLI & Architecture Spec

This covers **axitime**, the interpreter/command-line program that sits between the `.axitl` language and the hardware, and **libaxitl**, the reusable engine library it's built on. Companion to the separate **AxiTimeline Language Spec** (the `.axitl` grammar and layout algorithm — dates, pens, illustrations, fonts, side/lane resolution, event poles, tick marks, comments) and the hardware/electronics spec. This doc assumes the language spec's decisions and cross-references them where the two meet; it doesn't restate the grammar. The language spec's canonical copy is `docs/language-spec.md` in the same repo; treat any other copy of it as a possibly-stale snapshot. Last reconciled against the language spec's 2026-10-12 revision (required `width`, `now` reproducibility, paper-edge and window-clipping rules).

Both axitime and libaxitl are implemented in **Python**. Settled: the maturity of the `pyaxidraw`/`pyserial` ecosystem for talking to the AxiDraw's EBB board (and by extension the custom paper-transport microcontroller) outweighed other language options considered along the way (Rust, Go, C#) — none of those have anything close to the existing hobbyist/plotter prior art Python already has for this exact hardware. The language spec's own parser is built on **Lark** (a Python parsing library), consistent with this.

## Units

One rule, used everywhere a physical length appears — in axitime's own flags (`--start-offset`, `--length`, `--bleed`) and in `.axitl` source (`width=`, `length=`, `lane_height=`, `baseline_offset=`, `above_lane_height=`/`below_lane_height=`, `font_size=`, `ticks=`, an illustration's `height=`): a bare, unitless number is **millimetres**; `cm` and `m` suffixes are also accepted (`137cm`, `4.126m`), no space between the number and the suffix, and decimals are fine. This doesn't touch dates, priorities, or any other numeric field — only physical-length parameters. Internally, everything normalizes to millimetres as the one canonical unit once parsed, so there's a single representation flowing through the layout engine and renderer rather than mixed units needing conversion at odd points. `scale`'s own unit (`mm/year`, `mm/day`, etc.) is a separate kind of value — always an explicit rate, never a bare length — and isn't affected by this rule.

This is one shared convention across both docs (also recorded in the language spec, §14 there): axitime's CLI and `.axitl` source parse lengths the same way, so an operator or author can type whichever unit is most natural for what they're measuring — centimetres with a tape measure, millimetres for a fine correction, metres for a whole roll length — without the software caring which they chose. Output display (e.g. `list-pens`' ink-length report, or a confirmation prompt) is free to pick whatever unit reads most naturally for the magnitude involved; that's a display choice, not a parsing rule, and doesn't have to match whatever unit the operator happened to type in.

## Pipeline and core design principle

```
.axitl source ──check──> validation report (+ pen summary)
             \
              ──render──> SVG (full preview, or one file per pen)
                                     │
                                pen-specific SVG ──plot──> physical plotting
```

The central design decision: **`plot` never reads `.axitl` source directly.** It only ever consumes a pre-rendered, pen-specific SVG file. Because pen changes are manual and each pen requires its own invocation of the program, the layout has to be identical across every pass — any nondeterminism in re-parsing and re-laying-out the source between passes (a hand-edited file, floating-point ordering, whatever) would misalign strokes drawn with different pens on the same paper. Freezing the layout as SVG once, per pen, and treating that file as the only valid input to `plot` removes the possibility of drift entirely, and makes the SVG itself the auditable, inspectable "plan" — no separate plan format needed. (The language spec's own determinism section makes the same assumption from the other direction: layout is computed once per run, with deterministic tie-breaks throughout, since the project's plotting is one-shot.)

`render` should be able to produce all of a job's per-pen SVGs from a single invocation (one layout computation, one output per pen), rather than requiring the operator to re-run `render` once per pen — re-running it separately per pen reopens the same drift risk `plot` is designed to avoid. Each per-pen SVG should carry embedded metadata (a job hash of the source, computed after includes are expanded — see Job log, below, for full detail — the pen id/name, the axitime/libaxitl version, expected total stroke length, and, when the source's `timeline` ends at `now`, the resolved value of `now` — see "Pinning `now`", below) so `plot` can sanity-check the file it's been handed and confirm with the operator before it starts moving. Settled: this metadata lives in the SVG's standard `<metadata>` element — tested to survive an Inkscape open/modify/save round-trip intact, and further editor compatibility isn't axitime's problem to chase. Handling metadata it doesn't recognize in an otherwise-valid SVG is the editor's own obligation, not something `render` needs to work around.

Paper stock is assumed to always be wider and longer than the finished size, with the operator trimming to final dimensions afterward with a knife or guillotine — this is relevant wherever the interpreter introduces a boundary that will get cut. The language spec's `width` and `length` describe the *finished* size, not the stock; all ink stays inside the finished length (language spec §4.1).

## Library boundary: libaxitl

The parser, layout engine, and renderer aren't axitime-specific — they're expected to get reused by other programs (e.g. a future web front-end), so they belong in a separate, reusable library (**libaxitl**, paralleling the `.axitl` extension — easy to rename) that axitime depends on rather than owns. The library stays agnostic to where its input comes from and where its output goes: no **host** I/O — no filesystem, database, network, clipboard, or clock code reaching into the host's environment — lives inside it. axitime is one host of that library; other hosts source `.axitl` text differently (a web upload, a database row, a socket, a clipboard paste) and that's entirely their business, not the library's.

**Bundled data is not host I/O** (settled 2026-10-12). The library may read its own read-only package data, which today means the built-in fonts (language spec §3.8). That data is identical on every host and pinned by the library version, which is already part of the job hash, so it cannot make two hosts or two runs disagree. The rule exists to keep the library independent of the host's environment, not to forbid the library from shipping data.

Since libaxitl is Python, a future web front-end would reuse it either by running it as a small Python backend service the front-end calls over HTTP, or, if genuinely needed client-side, via something like Pyodide running the library directly in-browser — not a native compile-to-WASM story the way it might have been under Rust or Go. Not committed to either shape yet; noted here since it changes what "reused by a web front-end" actually looks like mechanically.

**Where library purity gets interesting: includes, illustrations and custom fonts.** All three require fetching more content by name, which is exactly the I/O the library isn't supposed to do. The fix is a loader the host supplies rather than the library assuming a source: `parse` takes the source text plus a caller-supplied `resolve(name) -> content` callable, returning raw text (for an `include`), raw SVG content (for an `illustration`), or raw SVG font content (for a custom `font="….svg"`; built-in fonts come from the library's bundled data and never go through `resolve`). The library joins each relative name onto the directory of the file that names it before calling `resolve`, so `resolve` always receives a name relative to the same root as the top-level source's own name. axitime's implementation does a local file read; a web front-end's might hit an API or IndexedDB; a strict linter that wants to forbid includes entirely could supply a loader that always throws. Only this one seam touches host I/O — everything downstream works from what's already been resolved.

**The same principle applies to `now`.** `timeline end=now` needs the current moment, and reading a clock is host behaviour just like reading a file. So `layout` takes the value of `now` as a host-supplied input rather than reaching for a clock itself; axitime supplies either the system clock or the operator's `--now` value (see "Pinning `now`", below).

**Public shape**, roughly:

- `parse(sourceText, resolve) -> AST` — the only stage that calls into host-supplied I/O. Per the language spec, include resolution is a **text-flattening preprocessing pass**, not AST-level splicing: `parse` walks `include` directives recursively, calling `resolve` for each and substituting the returned text in place (tracking which flattened region came from which source file + line, and applying each `include`'s `priority=`/`side=` modifiers to everything it pulled in), *before* the Lark grammar runs once over the fully-flattened result. This flattening pass has to be comment-aware (per the language spec's `//` comment syntax, §3.9 there) — a commented-out `include` line must not be followed, so the preprocessor recognises comments during flattening rather than leaving that entirely to the parser that runs afterward. The flattening pass also has to recognise multi-line declarations (language spec §3.10), so that `priority=`/`side=` given on an indented continuation of an `include` line are not missed. Cycle detection happens during this flattening, by checking each include against the chain of files currently being included; including the same file twice by different routes is not a cycle (its entities then fall under the duplicate rule, language spec §5). Once the grammar has run, `parse` loads every font the document uses (built-in from bundled data, custom through `resolve`) and every illustration, so the AST carries all the font and illustration data `layout` and `render` will need. Alongside the AST, `parse` exposes the flattened text itself and the list of every resource it fetched through `resolve` (kind — include, illustration or font — plus name and content), since axitime needs exactly those to compute the job hash and the per-resource hashes (see Job log) without re-reading anything.

**The flattened text** is a canonical form, so that edits which cannot change the layout don't change the job hash: comments removed, continuation lines joined onto their declaration with a single space, leading and trailing whitespace trimmed, each run of spaces or tabs outside a quoted string collapsed to one space (so re-aligning columns doesn't change the hash), blank lines dropped, LF line endings, and each `include` line replaced by the included file's flattened text with the include's `priority=` offset and `side=` override already applied to every entity line it pulled in (rewritten into that line's own `!`/`-` and `^`/`v` prefix). The grammar parses exactly this text, so it is a complete description of the document apart from the illustration and custom-font content fetched separately. Date/time literals inside `sourceText` (and therefore anywhere else a date is written, including `--from`/`--to` and `--now` below) use exactly the language spec's own date grammar (§3.3 there) — one date syntax for the whole system, not a separate CLI-only format.
- `layout(ast, now) -> ResolvedLayout` — pure function, no I/O, no clock; implements the language spec's side-resolution, lane-packing, event-pole, and label-collision algorithms (§§6–8 there). `now` is only consulted if the timeline's `end` is the keyword `now`; per language spec §3.6 it is truncated to the precision of the timeline's `start` and frozen. Besides the placements/pens/diagnostics described below, `ResolvedLayout` also exposes the resolved (truncated) value of `now` it used — so the host can fold it into the job hash and record it — and a `timeToPosition(date) -> mm` query — since mapping a calendar date to a physical position along the roll is already a core primitive the layout engine needs internally to place any dated entry, exposing it lets a host translate a date-based request into the library's native physical-mm terms without the library needing to understand dates itself anywhere outside layout resolution. It works over the language spec's internal continuous representation (proleptic Gregorian, seconds resolution, no year zero — 1 BC immediately followed by 1 AD) so BC/AD dates and mixed precision resolve consistently.
- `draw(resolvedLayout) -> Drawing` — pure function: every stroke the plotter will make, as a polyline in mm with its pen and draw stage, before any windowing, plus warnings about illustration content that can't be plotted. `render` is built on it, and `list-pens` measures each pen's ink from it.
- `render(resolvedLayout, options) -> svgString` — pure function; `options` covers pen filter (a specific pen id — one of the language spec's reserved pen/pencil/fountain keywords, or all), an optional `[start, length]` window in **mm** (the library's canonical unit — see Units, above), and bleed in mm. Deliberately stays physical-only and doesn't take dates directly — a host wanting a calendar-bounded render calls `timeToPosition` on its two dates first and passes the resulting mm window in. Kept in the library rather than duplicated in axitime, since another host might reasonably want a windowed or single-pen render too.

Everything else — reading the actual `.axitl` file off disk, reading the clock, writing the SVG string to a file, computing the job hash, embedding/reading the job-hash, `now`, and pen metadata used for `plot`'s sanity check, prompting the operator, driving the hardware, all CLI argument handling (including translating `--from`/`--to` into an mm window via `timeToPosition`, see below) — stays in axitime as the host program. axitime becomes a thin shell: read file → `parse` (with a filesystem-backed `resolve`) → `layout` (with `now` from the clock or `--now`) → `render` → write output, plus the plot-specific hardware execution that has no reason to live in a general-purpose library at all.

The API takes a complete string per source unit rather than a true incremental stream, for now — simpler, and nothing about `.axitl` files suggests they'll be large enough to need streaming; a host reading from a socket or clipboard just buffers fully before calling in. Worth revisiting only if that assumption breaks.

## Internal architecture: parser, layout engine, renderer

Three stages inside libaxitl (the language spec draws this as four boxes — include resolver, parser, layout engine, SVG generator — but the first two are one library call from the outside, per `parse` above):

**Parser (+ include resolution).** Flattens the include tree to text via the host-supplied `resolve` loader (comment-aware, as noted above), then runs the Lark grammar once over the result, producing an AST describing what the source *says* with no physical resolution yet.

AST shape: a `TimelineDocument` root carries the `timeline` directive's settings (required `width`; `start`; `end`, which may be the unresolved keyword `now`; scale/length; baseline position; per-side lane height and baseline offset; tick parameters; `open_end_style`; default font/pen) and an ordered list of entries. Each entry is a `Person`, `Event`, `Span`, or `Group` (a `Group` carries its own label/time range plus nested child entries, placed independently in the same shared per-side lane pool rather than nested inside the group's bracket). Every entry carries: its time value(s) (in the language spec's date grammar, at whatever precision the author wrote — year up to seconds, freely mixable; for a ranged entity, a start plus either an end or an explicit "open" marker; for an `event`, exactly one date), a raw priority delta (just the count of `!`/`-` prefixes — unresolved), an explicit above/below override or "auto," its pen (one of the reserved keywords, defaulting to `black`), attached illustration references (resolved content already embedded, per the loader design above — always attached to an entry, since standalone illustrations no longer exist in the language), and source provenance (originating source name + line, surviving the include-flattening so a conflict several includes deep still points at the real source to edit, plus a `member_of` tag for group children). Neither the parser nor the layout engine decides pen assignment beyond carrying it through — `list-pens` and per-pen `render` output are what aggregate it.

**Layout engine.** Consumes the AST (plus `now`) and produces a `ResolvedLayout`: the concrete baseline y-position; the finished width and the total required paper length in mm — the latter is simply the timeline's `length`, whether given directly or derived from `scale`, and never more, since all ink stays inside the finished length (language spec §4.1); the resolved value of `now` (if used); an ordered list of placed elements (each pointing back to its source AST entry, now with a resolved side, resolved lane/y-offset or pole length, and resolved x-extent along the roll); for each placed bar, whether it is **open or clipped at its start and/or its end** — open because the entity is ongoing, or clipped because it straddles the timeline window (language spec §§3.6, 4.2) — so the renderer knows where to draw the `open_end_style` cap, including at left-hand ends such as a person born before `start`; the list of pens the job needs, the axis pen (which draws the baseline and ticks) first (each pen's total draw length is measured by the renderer from the strokes it emits rather than by layout, since it depends on fill hatching, open-end caps and glyph strokes: settled 2026-10-12); each event's pole as the segments left after breaking it around other ink (language spec §8); a `timeToPosition(date) -> mm` query (see Public shape above); and a list of diagnostics (severity, message, source location — feeds `check`'s report; see `check`, below, for the catalogue).

**Renderer.** Walks a `ResolvedLayout` to emit an SVG string, in the language spec's own draw order (baseline + ticks, then span/group fills, then event poles and flags, then illustrations last) — full combined preview, or filtered to one pen, optionally windowed (in mm) with bleed (see Public shape above). Two renderer obligations come straight from the language spec: bars flagged open or clipped at an end get the document's `open_end_style` cap there (sawtooth by default, or sine), and **fill patterns must skip each bar label's bounding box** (plus a small margin; language spec §3.7), since a plotter can't knock hatching out from behind ink after the fact. All text — bar labels, event flags, tick labels — is emitted as stroke paths built from the font's glyphs, never as SVG `<text>`, which the plotter software does not draw. Layout and render use one shared text-shaping function, so the extent layout measured for a label is exactly the extent render draws.

**SVG conventions (settled 2026-10-12).** One SVG user unit is one millimetre, and `width`/`height` are given in mm, so plotter software draws at true size. Coordinates are the layout's own — x along the roll from the timeline's start, y across it from the finished top edge — so a stroke has identical coordinates in every file of a job, whole or windowed. The page (`viewBox`) spans the rendered window plus any bleed along the roll, and the finished width plus the crop-mark margin across it; every per-pen SVG from one render shares the same page, which is what lets separately plotted passes line up. Each pen is an Inkscape layer named after the pen.

**How the renderer draws** (implemented 2026-10-12; spacing values provisional, in `DrawStyle`):
- Everything is emitted as straight-line paths: curves (glyphs, sine caps, wave fills, illustration curves) are flattened once, in `draw`. Windows are cut geometrically at the window's edges (plus bleed), never with an SVG clip path, which plotter software ignores; so a windowed reprint draws exactly the strokes the whole job drew there.
- Every bar, a `group` included, is a closed outline (language spec §9). Open and clipped ends are drawn as a sawtooth or sine edge reaching 1.5mm into the bar, and its label starts clear of that edge. A pulled-out label's leader (language spec §7) is drawn in the bar's pen, broken like a pole; a bar's outline is broken around its own label only when that label runs past the bar as a last resort.
- Fills: `solid` is horizontal hatching every 0.4mm; `diagonal` and `crosshatch` lines every 2mm at 45°; `wave` horizontal sine lines every 2mm; `dots` short strokes on a 2mm grid. Patterns are anchored to the page rather than to each bar, so neighbouring bars and windowed reprints line up. A fill stops in a clean vertical edge 0.75mm either side of its bar's label, across the bar's full height, and leaves out any strip too narrow to hatch without stubs.
- Illustrations are flattened to the outlines of their shapes (paths including arcs, lines, polylines, polygons, rectangles, circles, ellipses, through nested groups and transforms), fitted into their box with the SVG default `xMidYMid meet`. Text, embedded images, `<use>` references and foreign objects can't be plotted and are left out; filled shapes are drawn as outlines; both are reported as warnings by `check`.
- `<metadata>` holds one `axitime:job` element (namespace `urn:axitimeline:job:1`) whose attributes record the pen (`all` for a preview), the stroke length in the file, the window and bleed actually used, and the libaxitl version, plus whatever fields the host adds (axitime adds the source file name, its own version and the resolved `now`; the job hash once its serialisation is fixed).

**Crop marks: settled.** Small crosshair marks, emitted by the renderer at a fixed physical interval — every 50cm along the whole roll — rather than only at bled boundaries specifically. A regular grid is simpler to generate and reason about than computing marks tailored to each job's particular start/end/bleed geometry, and it gives the operator a plain physical distance reference independent of the baseline tick marks' calendar-based (and not perfectly uniform) spacing. This is purely a `render`/libaxitl output-geometry concern — the `.axitl` author has no control over it and the layout engine doesn't need to know it exists. Crop marks are drawn in **pencil** rather than any of the job's own pens: a light, easily-trimmed-through mark that stays visually distinct from the actual artwork, so a stray crosshair that survives past a rough cut is never mistaken for a drawn stroke. Placement (settled 2026-10-12): a cross centred on each finished edge (y = 0 and y = width) at every 50cm from the start, arms 2.5mm each way, in `2H-pencil`. So the crop marks are the one piece of ink that crosses the finished width, by 2.5mm, on stock the trim removes; the stock needs at least that much spare on each side. Arms are cut short at the job's own two ends.

Neither the AST nor the `ResolvedLayout` need an on-disk serialization — `check`, `list-pens`, and `render` can each cheaply recompute both in-process from source. Determinism only has to be guaranteed once execution crosses into `plot`, and that's already handled by freezing the plan as SVG.

## Commands

### `axitime check <file.axitl>`

Parses the file, resolves includes, and runs the layout engine without touching hardware or producing drawing output. Reports:

**Fatal errors** — the content can't be drawn as written:

- Syntax errors, including the specific cases the language spec makes parse errors: a `timeline` without `width` (required, language spec §4), and a ranged entity (`person`/`span`/`group`) given a single date instead of a range or an open-ended start (§3.3).
- Broken includes, a cycle in the include tree, and missing illustration references.
- An unknown built-in font name, or a custom font file that can't be fetched or read (language spec §3.8).
- A bar or illustration that can't be placed on either side within the available width — no free lane band is left on either side (§4.1).
- An event whose base pole fits on neither side (§§4.1, 8.1).
- A `width` that exceeds the plotter's travel envelope (language spec §4 leaves this check to the interpreter; see Open Questions for where the envelope comes from).

**Warnings** — the engine compromised rather than failed:

- An entity lying wholly outside `start`–`end`, which is omitted (§4.2). An entity that only straddles the window is clipped silently; that's normal and not a warning.
- A bar label whose `font_size` won't fit inside `lane_height` (§7).
- An element that couldn't be pulled back inside either end of the paper (§4.1).
- A label interval coarsened to clear tick-label text width (§10.2).
- An illustration that couldn't be nudged clear of a pole (§§3.5, 8.1).
- A label-collision cluster left with its best achievable separation (§8.2).
- A duplicate entity across includes, resolved last-wins (§5).
- A label character the font lacks, replaced by a substitute (§3.8).

Also reports a summary of pens required for the job (name/id and rough count of strokes) — full detail is `list-pens`' job — and, for a timeline using `now`, the resolved `now` value.

Supports a `--json` (or similar) output mode so it can be scripted/gated on, since a paper roll is a real physical cost of getting this wrong.

Does not evaluate physical/motion feasibility (motor limits, transport speed) — that's explicitly deferred; see Open Questions. (The `width` check above is a static comparison against a configured limit, not motion analysis.)

### `axitime list-pens <file.axitl>`

Runs the same layout resolution as `check`, then renders the job in memory (writing nothing) to measure the strokes, and outputs, per pen: name/id (one of the language spec's reserved pen/pencil/fountain keywords) and total expected draw length, shown in whichever metric unit reads most naturally for the magnitude (see Units, above — this is a display choice, not a parsing rule). Intended for ink-supply planning ahead of a job. Standalone from `check` so it can be queried on its own.

Both `check` and `list-pens` could reasonably accept the same `--from`/`--to` bounds as `render` (below), to report warnings or ink usage for just a sub-range — cheap to add once `timeToPosition` exists, not yet committed to.

### Pinning `now`: `--now <date>`

Accepted by `render`, and also by `check` and `list-pens`, since all three compute the same layout and a timeline ending at `now` lays out differently on different days. The value is a single date in the language spec's date syntax (§3.3 there), e.g. `--now 2026-10-12`.

- **Without the flag**, `now` is read from the system clock, truncated to the precision of the timeline's `start` and frozen for the run (language spec §3.6).
- **With the flag**, the given value stands in for the clock reading and is truncated to `start`'s precision in exactly the same way. A `--now` coarser than `start`'s precision is rejected with a clear error rather than guessed at.
- **Why this exists:** the flattened source text still literally says `now`, so the source alone doesn't determine the layout. The resolved value is therefore folded into the job hash (see Job log), and recorded as its own readable field in the job log header and in each per-pen SVG's `<metadata>`, the same way the version is.
- **Operator workflow:** to re-render a job later — for example a windowed reprint of a damaged segment — pass `--now` with the value recorded in that job's log. The layout then reproduces the original and the hash matches. If the operator forgets, the layout may differ, the hash differs, and `plot` correctly reports that no existing job matches (overridable with `--force`, as for any mismatch).
- **Not applicable** when the source doesn't use `now`: the hash input, log header and SVG metadata carry no `now` field, and a `--now` supplied anyway has no effect (axitime says so in its output rather than silently ignoring it).

### `axitime render <file.axitl>`

Outputs SVG, with two modes:

- Full combined SVG (all pens together) — for visual review/preview, not for plotting.
- Per-pen SVG output (all pens from one invocation, e.g. one file per pen written to an output directory) — this is what `plot` consumes. As implemented: `axitime render <file> -o <dir>` writes `<name>-preview.svg` and `<name>-<pen>.svg` for every pen, crop-mark pencil included; `--preview-only` writes just the preview. Each file is tagged with the job hash, its pen id, the version, and (when applicable) the resolved `now`, as described above.

Windowing flags — two mutually exclusive ways to bound the output, since the two use cases think in different units:

- `--start-offset <length>` / `--length <length>` — physical bounds (see Units, above, for the shared length syntax), for reproducing a specific stretch of paper (see `plot`, below, where this pairing originates).
- `--from <date>` / `--to <date>` — calendar bounds, for pulling out a slice by the dates it covers rather than by ruler measurement. Covers two cases: reviewing a partial render before committing paper, and producing a finished, standalone slice of the timeline meant to be displayed on its own (a gift, a wall piece covering just one period) rather than spliced back into a larger roll. Each is a single point in the language spec's date syntax (e.g. `1963`, `1986-04-25`, `1986-04-25T14:00:00`, `44BC-03-15`) — settled, one date format for the whole system, not a CLI-specific range with its own separator. axitime resolves both dates to mm via `timeToPosition` and then runs the same window/bleed/clip logic as the length form — there's no separate code path once resolved, just a different way of specifying the same two numbers. `check`/`render` should validate that the requested range actually overlaps the timeline's span and error clearly rather than silently producing an empty or clamped result.

Since a calendar-bounded slice meant to stand alone isn't necessarily going to be spliced back into anything, `--bleed` still defaults on (2mm) for it as it does elsewhere — cheap insurance against a ragged trim — but is just as easy to zero out with `--bleed 0` for a clean edge when there's nothing to blend into.

### `axitime plot <pen-file.svg>`

Executes a physical plot from a single pen-specific SVG. On startup, checks the file's embedded pen id/job hash and confirms with the operator (expected pen, expected length) before moving.

`plot` only ever takes physical length bounds, never dates — it has no access to the AST or `ResolvedLayout` by design (that's the whole point of freezing to SVG), so there's nothing for a date to be resolved against at this stage. Any calendar-bounded job goes through `render --from/--to` first to produce the SVG, exactly like any other windowed plot. Likewise `plot` has no `--now`: the resolved `now` is already frozen into the SVG and its hash.

Flags:

- `--start-offset <length>` — skip ahead to a physical distance along the roll before starting (see Units, above, for the shared length syntax — a bare number is mm, `cm`/`m` suffixes accepted). This is how a partial plot gets resumed: the language spec's baseline tick marks (§10 there) give the operator a physical measuring reference — drawn in the first pen pass specifically so they survive to be measured against later — so an operator restarting after a pen change, a jam, or a power loss can measure the offset against a *labelled* tick with a T-square and hand it to the program directly (tick spacing isn't perfectly uniform at month/year intervals, so counting to a labelled tick matters more than assuming constant mm-per-tick). The renderer's own crop-mark grid (every 50cm, see above) offers a second, purely-physical measuring reference alongside the calendar-based ticks. There's no automatic position tracking — the software trusts the operator-supplied number. Some resulting edge misalignment is accepted as an operator problem to live with, not something the software tries to correct.
- `--length <length>` — stop after plotting this much distance past the start point, rather than continuing to the end of the file. Combined with `--start-offset`, this defines an arbitrary `[start, start+length)` window into the job rather than always running to the end. Two uses in mind: plotting a short run on scrap paper to check pen behaviour/ink flow before committing the roll (offset defaults to 0, so `--length` alone tests the start of the job), and reprinting just a damaged or botched segment on its own strip of paper to splice into the plotted sheet with tape or glue (offset set to the start of the damaged section). Strokes that cross a window boundary are clipped at it. The confirm-before-moving prompt should state the window plotted (e.g. "137.0–182.0 cm of 412.6 cm", picking whatever unit reads most naturally for the job's scale — a display choice, not a fixed unit) rather than just the full job length, so the operator can verify they're about to plot the segment they meant to.
- `--bleed <length>` (default 2mm, 0 disables) — extends strokes past a window boundary that will actually be trimmed, so a knife or guillotine cut lands on ink rather than risking a hairline gap from imprecise cutting or resumption. Applies only to boundaries that are genuine mid-job cuts, not to the natural ends of the job: the start edge is bled whenever `--start-offset > 0`, the end edge is bled whenever `--length` is given (i.e. the plot stops short of the job's natural end). An unbounded run from the true start to the true end needs no bleed — there's nothing on the other side of those edges to blend into. The extension runs along the roll's length axis only (the same axis `--start-offset`/`--length` are measured in), matching a guillotine cut across the roll's width, not a halo in every direction. Because the ink now overshoots the nominal boundary, the operator has no exact visual reference for precisely where the trim was meant to land at that specific cut — the renderer's 50cm crop-mark grid (see above) gives a nearby physical reference to measure the intended boundary from, rather than a mark placed exactly at it; that's judged close enough given a knife/guillotine trim was never going to be sub-millimetre precise anyway.
- `--dry-run` (or similar) — runs the full physical motion (transport advance and XY movement) with the pen held up, so the operator can watch the machine go through a job without marking paper. This is a flag on `plot`, not a separate command, since it's the same execution path minus ink.
- `--force` — proceeds even when the embedded job hash doesn't match any existing job log, or doesn't match the pen the operator says they've loaded. It's the operator's ink and paper being risked, not a call the software gets to make forever on their behalf. `--force` only skips the mismatch checks described in Job log, below — it doesn't skip the ordinary per-run confirmation prompt (expected pen, expected length) that appears on a clean, matching run too. Whatever mismatch got overridden is still written into the job log's entry for that run (e.g. "forced past hash mismatch: expected `<hash>`, found `<hash>`"), so the audit trail records that the safety check was bypassed, and why, even though `plot` didn't stop for it.

**Confirming the pen (settled 2026-10-12).** Before moving, `plot` shows what it is about to do — the pen, the window (e.g. "137.0–182.0 cm of 412.6 cm"), the ink in that window, the number of strips, and the job's earlier runs — and asks the operator to **type the pen's name** to start. A different answer refuses, unless `--force`, which records the mismatch in the log. Typing the name is harder to wave through on autopilot than answering y/n.

**Safe abort (settled 2026-10-12).** On Ctrl+C, a serial error or any other failure mid-plot, `plot` lifts the pen, returns the carriage home, switches the motors off and leaves the paper where it is. A closed terminal (SIGHUP, as when an SSH session drops) or a plain `kill` (SIGTERM) is treated exactly like Ctrl+C, and further interrupts are held off while the abort runs, so nothing can cut it short with the pen down (added 2026-10-13). It then writes the run's outcome to the log — cancelled or errored, with the stretch of the roll it was plotting — so the operator knows where to measure the `--start-offset` to resume from.

**The plotter's envelope and settings (settled 2026-10-12).** Built-in defaults describe an AxiDraw SE/A3; a small TOML file (`~/.config/axitime/plotter.toml`, or `--config <file>`) overrides them for a particular machine: its travel along and across the roll, how much of the roll it draws per strip, where the paper sits relative to its home position, pen heights and speeds, and the paper transport. `check` uses the same settings to flag a page wider than the plotter's travel across the roll (the page includes the crop-mark margin).

### Job log

Each physical job — potentially spanning several separately-invoked `plot` runs across different pens, days, or after an interruption — gets a human-readable, append-only job log recording its full history. Scoped to `plot` only: `render` and `check` stay stateless, as already established, since neither commits anything to paper.

The log's header identifies the job: the `.axitl` source path; the job hash (SHA-256, computed over the fully-resolved source *after* all includes have been expanded — not the raw pre-include text — combined with the axitime/libaxitl version that did the rendering, **the resolved value of `now` when the timeline uses it**, **and the SHA-256 of every illustration and custom font fetched through `resolve`** (settled 2026-10-12: these arrive outside the flattened text but change the layout, so editing an illustration or a font file must change the hash just as editing the source does), so that a version upgrade that might change layout behavior for otherwise-identical source, a re-render on a later day whose `now` resolves differently, or an edited illustration or font, gets caught the same way a source edit would be); the version number itself recorded separately as its own readable field (not just folded invisibly into the hash, so a human glancing at the log can see directly which version produced it rather than only inferring a change happened from the hash differing); the resolved `now`, likewise recorded as its own readable field whenever the source uses it (this is the value to hand back to `--now` when re-rendering the job later); and, since the job hash alone doesn't say *which* file changed if it ever stops matching, a SHA-256 of each individual include file, illustration and custom font involved, so a mismatch can be traced back to the specific file that moved. SHA-256's cryptographic properties are irrelevant here — it's just a convenient, effectively-collision-free fingerprint for the operator's own bookkeeping, not protecting against anything adversarial.

**Exact serialisation (settled 2026-10-12).** The job hash is the SHA-256, written as 64 lowercase hex characters, of this text in UTF-8 with LF line endings:

```text
axitimeline-job 1
libaxitl <version>
axitime <version>
now <value>                        (only when the timeline ends at now)
resource <kind> <sha256> <path>    (one per illustration and custom font)
source <length of the flattened text in bytes>
<the flattened text>
```

- The first line names the scheme and its version, so a future change can't be confused with this one.
- `now` is the resolved value at its truncated precision, in the language's date syntax: the value to pass back to `--now`.
- Each `resource` line gives the kind (`illustration` or `font`), the SHA-256 of the file's content with line endings normalised to LF and any UTF-8 byte-order mark removed (so a Windows checkout hashes the same), and the file's path relative to the main `.axitl` file's folder (so the hash doesn't depend on where axitime runs). Lines are sorted by kind, then path. Includes need no line: their text is already in the flattened source.
- The flattened text comes last, after its length, so nothing in it can be mistaken for a header line.
- Pen, window, bleed and other render options are not part of the hash: they vary between plot runs of the same job, and are recorded per run in the log.

The job log's header records the same per-file hashes, includes too, so a mismatch can be traced to the file that changed. Each SVG carries the hash as the `job-hash` attribute of its `axitime:job` metadata element.

The body is a chronological, append-only sequence of entries, one per `plot` invocation against this job: timestamp, which per-pen SVG was used, which pen, the window plotted (full job, or the `--start-offset`/`--length` bounds), and the outcome — completed, cancelled, errored (with the error message), or forced past a mismatch (with what the mismatch was, per `--force` above). Append-only rather than rewritten each time matters for the same reason the tick-mark resume mechanism exists: a crash or power loss mid-plot is a scenario this project already has to tolerate, and an append-only text file degrades gracefully if a run dies mid-write (worst case, one incomplete trailing line), whereas a structured file requiring a full rewrite each time risks corrupting the entire history in the same failure.

This also settles what `plot` does with the embedded job hash, left open earlier: at startup, `plot` looks for an existing log matching the SVG's embedded hash. Found → append a new run, continuing that job's history. Not found → it depends on whether the source has been plotted before (settled 2026-10-12). If no log exists for that source file at all, this is a new job's first pass: `plot` creates its log and starts it. If a log exists for the same source but with a different hash, an earlier pass was plotted from a different version — exactly the mismatch case the hash was meant to catch, surfaced to the operator as "no existing job matches this file" instead of relying on them to notice a discrepancy by eye, and blocking unless overridden with `--force` (which starts a new log for this hash and records the override). The full hash is what's used for this lookup, what's recorded in the log, and what's shown to the operator directly — there's no need to shorten it for human comparison. SHA-256 has an avalanche effect: changing even one character of the source (or bumping the version, or a different resolved `now`, both now folded into it) produces a hash that looks completely different, not subtly different, so a mismatch is obvious at a glance without the operator needing to compare it character-by-character. Truncating for display would only ever be a screen-space convenience, never a usability requirement.

**Where the header comes from.** `plot` never reads the `.axitl` source, so `render` writes everything the header needs into each SVG's metadata: the source file's name, the job hash, both versions, the resolved `now`, the job's total length, and one `axitime:file` element per file the job read (kind, path relative to the main file, SHA-256). `plot` copies them into the header when it creates the log.

**Log format.** Plain text. The header is `key: value` lines (`source`, `job-hash`, `axitime-version`, `libaxitl-version`, `now` when used, `length-mm`, and one `file:` line per file), then a line `---`. Each run then appends a `start` line when it begins (time, pen, SVG file, window, strips, any `--force` override) and an `end` line when it finishes (completed, cancelled or errored, with where). A crash leaves a `start` with no `end`, which is itself the record that the run was interrupted.

**File naming: settled.** The log filename is derived from the `.axitl` basename plus the **last 6 hex characters** of the job hash (e.g. `newton-timeline-9f21a3.log`), written alongside the rendered SVGs. Six hex characters is 24 bits — about 16.8 million possible values — which for a hobby project's own working directory keeps accidental collisions comfortably rare (even at a few hundred distinct job revisions over the project's lifetime, the odds of two colliding are well under 1%). It doesn't need to be higher than that, and it doesn't matter that it's the last 6 characters rather than the first or a slice from the middle — SHA-256's avalanche effect makes any fixed-position slice equally well-distributed. Whichever 6 characters are used is purely a lookup convenience, not the actual identity check: `plot` always verifies the *full* hash recorded in a candidate log's header against the SVG's embedded hash before treating it as the same job. That means even the rare filename collision can't cause two unrelated jobs to be silently conflated — a suffix match with a header mismatch is just treated as "no existing job found," same as no file at all.

## Open questions / deliberately deferred

- **Physical motion feasibility checking** (motor limits, transport speed, whether the EBB firmware does its own adjustment) is not part of `check` or `render` yet. Deferred until after physical testing shows what actually needs validating — premature to design against unknown firmware behavior.
- How a future web front-end actually reuses libaxitl (a Pyodide-hosted client-side copy vs. a small Python backend service it calls) isn't decided — a direct consequence of libaxitl being Python rather than something with a native WASM target, not resolved here.
